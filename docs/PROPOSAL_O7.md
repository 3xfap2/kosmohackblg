## Принципы

- Любое число — из ядра и модели организаторов. ИИ ничего не считает и не решает.
- Каждая функция подтверждается примером или сравнением «с / без» в `results/` (требование О7).
- Vercel Hobby: 1 vCPU, ≤ 300 с на запрос. Тяжёлые прогоны — заранее в `experiments/` → `results/`.

## Ответ Codex

Оценка после обязательной части ядра:

| # | Решение | Оценка Codex |
|---|---|---|
| F1 | После обязательных экспериментов | Реально как три независимые ветви до `min(конец смены, текущий шаг + 48)`. Для полного P02 три ветви могут занять минуты. «План не меняли» надо исполнять сохранённый кэш без ремонта; при недопустимой команде — ожидание с причиной. В интерфейсе явно писать горизонт оценки. |
| F2 | Узкий MVP после F1/F3 | Начать с проверяемых кандидатов: принудительный приоритет задания, затем увеличение начального заряда производного сценария. Принудительное назначение без перепланирования остальных аппаратов даёт контрфакт, но не минимальное изменение; так его и подписывать. Поиск настоящего минимума дороже и требует отдельной оптимизационной постановки. |
| F3 | Можно переиспользовать механику F1 | `preview_event` = ветвь + атомарный `apply_event` + прогон до максимального срока новых заданий, но не дальше смены. Возвращать выполненные/вытесненные задания и дельты только при одинаковом конечном шаге. |
| F4 | Только как прогноз с оговоркой A5 | Надёжнее прогнать сохранённый план через официальную `Session`, чем выдавать `physics.forecast` за факт. Прогноз CP-SAT по температуре приближённый и не гарантирует нижнюю границу энергии. Результат помечать как прогноз до горизонта, каждую команду проверять официальной моделью. |
| F5 | Офлайн в `results/`; онлайн только P01 | `+10% солнца` допустимо как командное допущение. Лимит downlink и `+1 аппарат` не входят в контракт `Overrides`; это отдельные экспериментальные производные сценарии с явной маркировкой, не изменение условий организатора. |
| F6 | 5 точек офлайн | Текущий A4 — фиксированная эвристика, параметра веса в контракте ещё нет. Достаточно 5 заранее рассчитанных весов, но сначала вес надо сделать параметром и тестом доказать, что точки воспроизводимы. Не называть график границей Парето без проверки недоминируемости. |
| F7 | Сократить до 10–20 наборов на P02 | 50 × 2 полных гибридных прогонов слишком дорого для оставшегося времени. Seed должен порождать только допустимые события, а сравнение — использовать одни события и условия. Расширить до 50 после закрытия матрицы. |
| F8 | Метрика да, новый режим пока нет | Метрика по доступности downlink берётся из сценария; метрика фактического использования — из trace. Это разные показатели. Мягкий штраф может ухудшить P3/выручку и требует отдельного критерия выбора, чувствительности и доказательства; сейчас не добавлять в основной планировщик. |
| F9 | Реально и дёшево | Агрегаты по официальному trace надёжны. «Рекомендуемые окна» являются прогнозом: помечать отдельно и валидировать через модель. Глубину разряда определить однозначно до реализации (например, максимум SOC − минимум SOC по смене). |
| F10 | Реально после завершения анализа потерь | Добавить `loss_summary` как агрегат только доказанных `loss`; отдельным числом показывать потери без установленной причины. Не распределять их по категориям эвристически. |

Приоритет ядра после обязательной части: F3 → F1 → F4 → F2. F5–F10 делать только если
обязательные эксперименты, сверка чисел и деплой уже зелёные. AI-1 должен цитировать факты
из `explain/trace/jobs`, AI-2 всегда требует подтверждения JSON оператором до `apply_event`.

Отдельный риск деплоя: встроенные `RunRecord` компактны, но `export` содержит исходный сценарий.
Результаты P02 с полным trace превышают 5 МБ, P04 — 7 МБ. `include_trace=False` обязателен для
веб-ответа; проверенный экспорт P04 без trace — около 2,5 МБ. Загруженный `inline`-сценарий остаётся
в каждом запросе, поэтому его размер надо ограничить до безопасного уровня ниже лимита Vercel 4,5 МБ.
