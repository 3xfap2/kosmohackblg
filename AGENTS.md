# AGENTS.md — правила для Codex и Claude в этом репозитории

Проект «Созвездие» — веб-сервис автономного управления спутниковой группировкой
(КосмоХакатон 2026, кейс «Автономное управление спутниковой группировкой»).
На всю работу — сутки. Постановка, описание данных и критерии — в `../Кейс 1/*.pdf`.

## Источники правды

1. `CRITERIA.md` — матрица критериев. Каждая работа закрывает конкретный код (О1–О7, Т1–Т6).
2. `docs/CONTRACT.md` — типы и функции между ядром и интерфейсом. Меняет только Claude (автор);
   если нужно изменение — написать в `docs/HANDOFF.md` и дождаться правки контракта.
3. `results/summary.json` — единственный источник чисел для документов и презентации.
4. `docs/ASSUMPTIONS.md` — настройки и допущения команды (не условия организатора).

## Владение папками

| Папка | Владелец | Что внутри |
|---|---|---|
| `model/`, `data/`, `examples/` | организаторы | Не редактировать. Только читать. |
| `core/` | **Codex** | Сценарии, запуски, планировщики, события, анализ потерь, сравнение. Без импортов FastAPI/веба. |
| `tests/` | **Codex** | pytest. |
| `experiments/`, `results/`, `scripts/` | **Codex** | Генератор выгрузок (одна команда, фиксированный seed), сверка чисел. `results/` коммитится — это артефакт сдачи. |
| `server/` | Claude | FastAPI поверх `core/service.py` (Vercel Function). |
| `web/` | Claude | React + Vite + TS. Только отображение, никаких расчётов. |
| `docs/`, `README.md`, `CRITERIA.md`, презентация, деплой | Claude | Допущения планировщика в `docs/ASSUMPTIONS.md` правит Codex. |

В чужую папку — только через `docs/HANDOFF.md`. Если оба правят один файл — остановиться и договориться.

## Правила

- Маленькие частые коммиты. В сообщении коммита — код критерия: `[Т3] ...`. Перед работой — `git pull`/проверка свежих изменений.
- После каждого изменения ядра: `pytest`, генератор результатов, сверка чисел. Красные тесты не коммитить.
- Любое исполнение действий — только через `model.operations.Session` (Т1). Физику сами не пересчитываем для учёта;
  прогноз внутри планировщика допустим, но итог всегда считает модель.
- Планировщик видит только `session.observation()` и `session.env.s` — никаких будущих событий (Т3).
- Не выдумывать числа. Нет данных — `[НУЖНЫ ДАННЫЕ]`.
- Никаких абсолютных путей и секретов в коде. Конфиг — через аргументы/переменные окружения (`.env.example`).
- Код на Python 3.12, зависимости — `requirements.txt` с версиями. Комментарии и сообщения пользователю — по-русски.

## Задачи Codex (по порядку)

Уже есть черновик планировщиков в `core/planner/` (написан Claude до раздела ролей, **ни разу не запускался**):
`physics.py` (прогноз ΔE и температуры по формулам модели), `base.py` (интерфейс `Planner`, `Admission` —
согласование действий шага как в модели), `edf.py` (простое правило «ближайший срок»), `horizon.py`
(CP-SAT на скользящем окне с пересчётом при событиях/отказах). Бери, проверяй, правь или переписывай — это твоя папка.

1. **[Т2][Т4] Проверить планировщики.** Прогнать EDF и horizon на P01–P04 × обе цели. Проверить: нет отклонённых
   моделью команд (кроме ожидаемых), время расчёта P02/P04, итоговые показатели. Детерминированность CP-SAT:
   фиксированный seed + детерминированный лимит (`max_deterministic_time`) или `interleave_search` — выбрать и
   зафиксировать; повторный запуск должен давать те же команды.
2. **[Т1][Т3] `core/service.py` по контракту** (`docs/CONTRACT.md`, раздел «Python-интерфейс ядра») +
   `core/errors.py`. Запуск = `Session` + планировщик + история целей + отклонённые события. `fork()` копирует
   и сессию, и состояние планировщика (deepcopy). `run_metadata` заполнять по описанию данных, включая
   переключения целей и развилку ветви.
3. **[О3] Анализ потерь** (`core/analysis.py`): статусы заданий и `LossReason` в двух группах —
   `problem_limit` (доказуемо: нет/мало шагов с контактом в окне, аппарат недоступен всё окно, энергетическая
   верхняя граница) и `planner_choice` (по журналу: исполнитель занят другим заданием, канал занят, энергия
   ушла на другое, калибровка не вовремя, начато и не завершено). Плюс `explain()` для задания и аппарата на шаге.
   Статический анализ «доказуемо невыполнимо» — ещё и в `ScenarioInfo.provably_infeasible_jobs`.
   Пример из данных: у JOB-0007 (P02) work_steps = 2, а в окне у S01 всего один шаг с контактом.
4. **[О4] `compare()`**: одинаковое происхождение ветвей проверять по `state_digest` на шаге развилки;
   вердикт для цели с порогом «сопоставимо».
5. **[Т1][Т3] Тесты:** экспорт → `python model/operations.py --result` → та же сводка (все сценарии и ветви);
   события — повторный id, прошлый/будущий шаг, битый JSON, частичное применение пакета невозможно, состояние
   не меняется после отказа; ветви независимы; смена цели пишется в историю и влияет только на будущее.
6. **[Т4][О1][О2] `experiments/run.py`** → `results/summary.json` + `results/runs/*.json`:
   EDF vs horizon × P01–P04 × обе цели; P02 + `examples/events_demo.json` с перестройкой и вариант
   «без перестройки» (для цепочки «событие → нарушение → реакция → что сохранено»); P03 как дефицит.
   Фиксировать сценарий, цель, сообщения, настройки, версию алгоритма.
7. **[О6] `scripts/check_numbers.py`** — сверка чисел в `docs/*.md`, `README.md` с `results/summary.json`.

Каждую задачу закрывать коммитом с кодом критерия и строкой в `docs/HANDOFF.md` («что готово, как проверить»).
