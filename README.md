# Созвездие — автономное управление спутниковой группировкой

КосмоХакатон 2026, кейс 1. Веб-сервис для оператора наземной смены: сам распределяет задания
между 48 спутниками, следит за зарядом, температурой, калибровкой и окнами связи, перестраивает
план после каждого сообщения (срочные заявки, отказы, отмена сеансов), объясняет потери
и сравнивает варианты продолжения из одного состояния.

**Все итоги считает официальная модель организаторов** (`model/`, без изменений): планировщик
только отдаёт команды. Числа ниже — из `results/summary.json` (генератор `experiments/run.py`).

**Как устроено.** Расчёт идёт на сервере: FastAPI (`server/`) поверх ядра (`core/`), каждое действие исполняет модель
организаторов. Браузер (`web/`) только показывает смену и хранит её у себя — регистрации нет по условию постановки, поэтому
у каждого проверяющего свои смены. Чтобы передать смену другому человеку, на странице смены есть «Файл смены для переноса»,
а в «Моих сменах» — «Загрузить смену из файла» (подпись и версию проверяет сервер).

**Для проверяющих:** карта «критерий → где реализовано → как проверить → результат» — [`CRITERIA.md`](CRITERIA.md).

| P03 дефицит энергии | 299 / 334 | 314 / 334 | 314 / 334 |
| P04 перегрузка | 1232 / 1692 | 1649 / 1692 | 1649 / 1692 |

  коммерческий режим приносит больше выручки, чем приоритетный (P02 $27 352 против $27 151); в маленькой P01 выручка равна.
  Цена выбора цели на P04: +$31 423 выручки за −391 срочных.
- Сообщения во время смены (P02 + `examples/events_demo.json`, приоритет): из 4 заявок в сообщениях выполнено 3, старый план — 0
  (четвёртая пришла во время отмены всех сеансов связи); срочные 307 → 310, просрочено 81 → 72; из предложений старого плана 22 не проходят
  проверку допуска (недоступный спутник, нет связи, нужна калибровка) и отбрасываются до отправки модели.
  Простое правило с теми же сообщениями: срочные 302, просрочено 79 (у нас 310 и 72).
- Устойчивость (`results/research.json`): 12 случайных наборов отказов и отмен связи (seed 7) — эвристика лучше простого
  правила во всех 12 и на P02, и на P04. Чувствительность настроек CP-SAT (окно 24/36/48/72, перестройка 3/6/12, ценность
  остатка энергии 0/0,25/0,5/1) на P02: срочные 314–315, выручка $27 146–27 216 — результат устойчив к настройкам.
- Энергия в перегрузке (P04): спутнико-шагов ниже резерва у нас меньше, чем у правила, — 293 против 491 (приоритет) и 276 против 488
  (коммерция). Разбор журнала: ниже резерва спутники уходят только в ожидании в тени, когда работа внутри тени съела запас, а до
  солнца ещё несколько шагов (подогрев ни при чём, до критических 20 % не доходит никто). Эвристика 1.3 в тени откладывает

  Было 533 и 564; цена — 3 срочных из 1692 в приоритетном режиме (1652 → 1649), в коммерческом срочных +1, выручка −0,18 %;
  P01–P03 не меняются (тест `test_shadow_guard_keeps_p04_above_reserve_more_than_edf`).
- Вклад CP-SAT измерим (`cpsat_gain` в `results/summary.json`): решатель принимается только там, где его план лучше
  эвристики на том же окне, и вклад принятых планов по оценке окна — $37 на P02, $48 на P03 и $135 на P04 (приоритет).
  Это и есть честный масштаб: основной выигрыш над простым правилом даёт эвристика, решатель добирает на отдельных окнах.
- Слабые места (показываем сами): CP-SAT в коммерческом режиме P04 не принят ни разу — итог равен эвристике (там же один
  запасной режим решателя); защита заряда в тени в приоритетном режиме P04 стоит 3 срочных.
- 32 из 32 прогонов повторены моделью организаторов с тем же итогом, каждый рассчитан дважды — команды совпали побитно; отказов модели 0.

## Как проверить (тесты — меньше минуты; полный пересчёт результатов — около 25 минут)

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt        # Linux/macOS: .venv/bin/pip
.venv/Scripts/python -m pytest -q                     # все тесты, включая повтор 32 сохранённых выгрузок
.venv/Scripts/python -m experiments.run --repeat --events   # пересчитать results/summary.json (~15 мин, CP-SAT)
.venv/Scripts/python -m experiments.extended          # расширенная модель → results/extended_summary.json
.venv/Scripts/python -m scripts.check_inputs --case "<папка Кейс 1>"   # файлы организаторов не изменены
python tests/e2e/browser_checks.py                    # браузерные проверки (нужны uvicorn и vite, см. файл)
.venv/Scripts/python -m experiments.demo_losses       # таблица доказательств потерь демо-смены
```

Повтор выгруженной смены официальным скриптом организаторов (кнопка «Скачать выгрузку JSON» в консоли):

```bash
.venv/Scripts/python model/operations.py --result sozvezdie_<id>.json --output replay.json
```

## Запуск сервиса

```bash
.venv/Scripts/python -m uvicorn server.main:app --port 8000     # API
cd web && npm ci && npm run dev                                 # интерфейс: http://localhost:5173 (прокси /api → :8000)
```

Сборка одним сервисом: `npm --prefix web run build` — FastAPI отдаёт `web/dist`. Деплой: Vercel (`vercel.json`,
Python Function `server/main.py`, лимит 300 с на запрос — расчёт идёт кусками по 240 с).

Окружение: Python ≥ 3.12 (проверено на 3.12.7), Node.js ≥ 20 для сборки интерфейса.
Переменные окружения (`.env.example`): `ANTHROPIC_API_KEY` — необязательно, без ключа ИИ-ассистент отвечает
шаблонами по фактам журнала; `SOZVEZDIE_AI_MODEL` — модель ассистента; `SOZVEZDIE_STEP_BUDGET_S` — бюджет одного
запроса расчёта в секундах (по умолчанию 240); `SOZVEZDIE_RECORD_SECRET` — секрет подписи записи смены
(сервер без состояния подписывает запись HMAC, и переписать историю на клиенте нельзя; на развёртывании задать свой).
Публичный сервис без авторизации защищён по нагрузке: частота запросов с одного адреса ограничена (расчёт — 120, функции — 90,
помощник — 20 запросов в минуту; это выше рабочего темпа оператора и автопилота), тяжёлые расчёты и обращения к помощнику стоят в очередях.
Без `SOZVEZDIE_RECORD_SECRET` локально создаётся случайный секрет в `.local_record_secret` (вне git); на Vercel сервер без
него не стартует. Тяжёлые расчёты (оценка последствий, «Можно ли было выполнить?», прогноз, what-if, компромисс, стресс,
турнир) — не больше трёх одновременно на экземпляр; запрос — до 8 МБ и только с Content-Length (на Vercel лимит платформы — 4,5 МБ).

## Как пользоваться (сценарий оператора)

1. **Консоль** — `/console`: сразу открывается демо-смена (P02 + сообщения организаторов, остановлена в 12:00).
2. **Загрузка сценария** — «Новая смена»: выбрать P01–P04 или «Свой сценарий» (JSON формата cosmo-B-ops-1.0, проверяется
   моделью). «Условия эксперимента»: множитель солнечной мощности, начальный заряд аппарата, приоритет задания,
   известный период недоступности аппарата — сохраняются новым сценарием. Выбрать цель и алгоритм → «Создать смену».
3. **Ход расчёта** — «+1 шаг», «+1 час», «До конца» или поле «Остановиться перед шагом N». Длинный расчёт идёт с индикатором.
   **Автопилот** — смена идёт сама по часу; после каждого часа прогноз на 2 часа; остановка только при новом поводе
   вмешаться (риск заряда, срочное задание под угрозой, в демо — приход сообщения).
4. **Сообщение** — вкладка «Сообщение»: форма (аппараты + конец интервала для недоступности или отмены сеансов),
   JSON (новые задания или любое сообщение) или текст (черновик через ИИ, подтверждает оператор).
   «Оценить последствия» — последствия сообщения: три ветви из одного состояния (без сообщения, старый план, перестройка)
   и что изменится в плане (какие спутники получат другие назначения). Некорректное или повторное
   сообщение отклоняется с объяснением, состояние не меняется.
5. **Сравнение** — «Ветвь с другой целью / алгоритмом» из текущего состояния → «Сравнить…» (вердикт по цели или «сопоставимы»).
   «Исследование смены → Турнир стратегий»: простое правило и эвристика × две цели из текущего момента до конца смены,
   лучшая стратегия для каждой цели и кнопка «Ветвь».
   Все смены браузера — «Мои смены».
6. **Разбор** — таблица заданий → «Почему?»; клик по спутнику на карте — его паспорт; «Отчёт о передаче смены».
7. **Сохранение** — «Скачать выгрузку JSON» (исходный сценарий, сообщения по порядку, команды, шаги, сводка, цель,
   параметры и версия алгоритма) → повтор `model/operations.py --result` (см. выше).

**Примеры сохранённых расчётов**: `results/runs/*.json` — 32 смены в формате выгрузки модели организаторов
(сценарий, сообщения, команды, сводка, трасса); любую можно повторить той же командой `--result`.

## Метод

Каждые 6 шагов (30 мин) и сразу после сообщения, смены цели или отказа команды планировщик решает сам:

1. **Эвристика по цели** (`core/planner/greedy.py`, основа): порядок заданий под цель (приоритет → запас времени
   или стоимость на оставшуюся возможность связи — стоимость / число шагов до срока, где у допустимых исполнителей есть контакт), не берёт задания, которые уже не успеть по сроку или по шагам связи (A10),
   исполнитель — допустимый спутник с наибольшим зарядом, в тени — только тот, кто простоит до конца тени не ниже резерва
   (иначе задание откладывается, если окна связи будут и позже), калибровка заранее (A9).
2. **CP-SAT на 4 часа** (`core/planner/horizon.py`, OR-Tools): ищет план на 48 шагов с подсказкой из плана
   эвристики; план принимается, только если официальная модель на том же окне подтверждает, что он не хуже (A7).
3. **Простое правило EDF** (`core/planner/edf.py`) — точка отсчёта для сравнения.

Допущения и настройки — `docs/ASSUMPTIONS.md` (A1–A13). Детерминизм: seed 7, один поток, лимит в единицах работы (A6).

## Объяснение потерь

Невыполненное задание помечается как **ограничение задачи** (с проверяемым доказательством — окно, шаги связи,
исполнители, отказы) или как **решение алгоритма** (конкуренция в журнале; кнопка «Можно ли было выполнить?»
проверяет моделью и показывает цену). Без доказательства — «причина не установлена».
Демо-смена в 12:00: 10 потерянных P3 — 9 ограничений задачи, 1 решение алгоритма (`results/demo_losses.json`).

## Расширенная модель (О7): ориентация, светотень, связь

`core/extended.py` наследует `Environment` организаторов, файлы `model/` не меняются:

- **Ориентация и светотень** (A11): при наведении на Землю, ретранслятор или звёзды панели отвёрнуты — генерация на свету ×0,6; в тени без изменений.
- **Разворот** (A12): смена режима наведения — 0,5 Вт·ч.
- **Служебный сеанс связи** `{"action": "link"}` (A13): держит канал с Землёй без задания; занимает общий канал (лимит 2).
  Планировщик с `link_guard` следит, чтобы на шаге с контактом хотя бы один спутник был на связи.

Результаты (`results/extended_summary.json`): P02, приоритет, эвристика с учётом ориентации без удержания связи и с ним —
среди шагов с доступным контактом доля шагов со связью с Землёй 82,9 % → 96,2 % без потери срочных (315) и выручки; учёт ориентации сильнее бьёт по простому правилу (P03 299 → 263, P04 1232 → 828), чем по
эвристике (314 → 310, 1649 → 1564). Учёт цены ориентации при выборе исполнителя даёт небольшой и не всегда положительный эффект.
У удержания связи есть цена там, где ресурса мало: P04, коммерция — срочные 846 → 833, выручка $147 348 → $146 678;
P03, коммерция — срочные 308 → 305 (доля шагов со связью при этом растёт на всех сценариях).

## Структура

```
model/        расчётная модель организаторов (без изменений)
data/         сценарии P01–P04 (без изменений)
examples/     пример сообщений events_demo.json
core/         ядро: service.py (запуски, события, ветви, выгрузка), planner/, analysis.py (потери),
              features.py (функции О7), extended.py (расширенная модель)
server/       FastAPI поверх core — без состояния; ai.py — ИИ-ассистент (идентификаторы и числа ответа должны
              присутствовать в фактах журнала, иначе — шаблонный ответ; причинность ответа этим не доказывается)
web/          интерфейс (React + Vite + TypeScript)
experiments/  run.py, extended.py, demo_losses.py → results/
tests/        pytest
docs/         CONTRACT.md (форматы и API), ASSUMPTIONS.md, HANDOFF.md
```

Форматы: запуск хранится в браузере как `RunRecord` (`docs/CONTRACT.md`) и передаётся в каждом запросе;
выгрузка — формат результата модели организаторов (`initial_scenario`, `events`, `commands`, `summary`).

## Ограничения

- Модель — расчётная, не телеметрия; расширенная модель — наши допущения A11–A13.
- План смотрит на 4 часа; страховка A7 действует внутри окна, не для всей смены. При равной оценке окна она выбирает план
  эвристики; работа, потраченная на задания, которые не завершатся, в оценку окна не входит.
- CP-SAT не планирует задания, которые нельзя завершить внутри своего окна (частичная работа с переходом в следующее окно
  не моделируется), и считает температуру по траектории эвристики (A5).
- Ветвь «с другим алгоритмом» использует стандартные настройки этого алгоритма; настройки прежнего в неё не переносятся.
- CP-SAT чаще подтверждает план эвристики, чем улучшает его: принят в 6, 5 и 1 из 48 перестроек (P02, P03, P04, приоритет)
  и в 7, 2 и 0 из 48 (коммерция).
- Эвристика коммерческого режима v1.1: порядок «стоимость на шаг работы» (v1.0) в P02 и P03 давал выручку ниже приоритетного
  режима; порядок «стоимость на оставшуюся возможность связи» это исправил — закреплено тестом
  `tests/test_greedy.py::test_revenue_goal_earns_at_least_priority_goal`.
